# The Relay — write-up

All numbers come from `results/results.csv` (tables generated by `exp/make_tables.py`) or the logs named beside them.
Stand-in figures are simulated; every stand-in assumption is listed in NOTES.md ("NOT measured on real Groq").

## 1 What I built and why
A cited question-answering pipeline over the three papers: route (explicit paper names only) → hybrid retrieval
(BM25 + bge-small, reciprocal rank fusion, 200-token chunks, top-8 ≈ 1,600 context tokens) → gate (semantic top-1
cosine ≥ 0.60, else refuse with zero model calls) → generate (gpt-oss-120b, cites [S1]–[S8] or says NOT_IN_PAPERS) →
deterministic citation check → judge on the cited chunks only (gpt-oss-20b) → at most one correction → citations
rendered from chunk metadata. Answers are buffered: nothing unverified is released. Every model call goes through a
per-model token-bucket limiter. **The decision that shaped it most:** the free tier's 8,000 tokens per minute, not
requests per minute, is the binding limit — a generate call averaged 2,093 tokens and a judge call 504–1,372 in the real
runs, and the limiter reserves ≈ 2.6K per generation, so 120b serves about **3 answers a minute** (≈ 3.05). That made the judge a separate model (separate quota), the gate a zero-token refusal,
and capacity planning a token problem.

## 2 The real service and my stand-in
Limits came from the console, the response headers on every call (32 probe calls, then 13 pipeline calls), and one real
429 (Table 1). The stand-in (`standin/server.py`) speaks the same API with streaming, resamples latency from the 131 real
200-responses by model and prompt size, keeps a continuously refilling 8K-per-minute bucket per model, returns 429s with
the real body and headers, replays the real graded answers, and can inject 5xx and slow successes. **Least like the
real thing:** slowdown under concurrent load (5% per extra in-flight request is invented — we never sent concurrent
real calls) and how Groq charges a call while it is in flight (medium-low confidence).

## 4 Where the time goes
Slowest real request with all calls in one session: baseline A01, 26,264 ms (`results/phase5_log.jsonl`).
**Waiting:** 23,413 ms of our own per-minute pacing before the first call (the previous question had drained the bucket)
plus 1,404 ms of Groq queue time inside the four calls. **Working:** ≈ 1,448 ms of generation and judging.
**Retrying:** 0 HTTP retries; the judge rejected attempt 1 (an unsupported claim), so a correction plus a second judge
call (1,393 ms of call time) is re-work. All of it came **before the first token**: answers are buffered, so the user
sees nothing until the judge approves. The model's own first token arrived 680 ms into the first call.

## 5 When a limit is hit
**Per-minute:** the limiter learns the limit from the first response's headers, reserves prompt + max_tokens before each
call, lets in-progress work (judge, correction) go before new questions, and sheds a request early when the wait would
pass the user's patience. Shed users get the fallback ladder: a validated cached answer, else the top-2 passages with
citations (zero tokens), else an honest refusal. New questions are delayed first; nobody is dropped silently.
**Per-day:** no retry (a per-day 429 is final); the same ladder serves everyone until the budget returns.

## Retrieval: quality versus cost
Retrieval-only recall within a ~1,600-token budget (40 questions, zero tokens): BM25 34/40, hybrid 34/40, semantic
28/40 at 200-token chunks; 800-token chunks drop to 30 / 31 / 25 because only two fit the budget (scoring by the best
piece instead of the averaged vector did not help: 22 vs 25). I chose **hybrid, 200, top-8** (same recall as BM25, but
semantic covers paraphrases) with BM25 as baseline and 800/top-2 as the wide-context comparison (Table 3). **When the
limit is close** I do not shrink retrieval: top-4 would raise 120b capacity from ≈ 3.05 to ≈ 4.40 answers a minute but
cut recall to 27/40 (hybrid) or 31/40 (BM25), and overload arrived at ~3× capacity anyway.

## How this library will mislead a naive retriever
1. **Moshi's dialogue-transcript appendix** (pp.63–64, full of "USER: … MOSHI: …") outranks the abstract on BM25 for any
   question containing "Moshi" — "What theoretical latency does the abstract report for Moshi…?" (R13).
2. **"Layers" is in all three papers.** "How many identical layers are in the Transformer encoder stack?" (R01) put a
   Dynamic Chunking chunk first and Moshi's "8 layers" third; the top three cosines were within 0.012.
3. **Tables lose their rows in plain text extraction.** Attention's Table 2 came out as ten model names and a separate
   column of eight EN-DE scores, so "What BLEU did the base model get?" (R08) cannot be paired by position; I re-extract
   table pages in layout mode.

## 6 Retries
Policy: retry only per-minute 429s, 5xx and transport errors; never a per-day 429; at most 2 per call; wait the larger
of `retry-after` and an exponential backoff with jitter; a global retry budget of 10% of calls; never if the wait
passes the user's patience; every retry waits its turn in the limiter. **Retrying made things worse** with a naive
client (every 429 retried immediately) on the same stand-in load: in overload, 74 of 133 users gave up against 1 with
the limiter, with 1,719 retries; in a burst, 29 of 63 against 0 (retry comparison table above).

## 7 What the person sees
At 3 pm the daily budget is gone. A question whose answer was already validated today gets that answer, marked as
cached. Otherwise they get, within a fraction of a second: "I can't generate a checked answer right now (capacity
limit). The most relevant passages are:" followed by two quoted passages with paper, section and page. An off-topic
question is refused as usual. In the stand-in's daily-exhausted run (Table 2b) 2 questions got generated answers before
the budget ran out; overall served 100.0% / full answer 59.5%.

## 8 What I'm unsure about, what I left out, what I learned
**Least certain:** how Groq charges a call while it is in flight. If it does not reserve max_tokens at admission, the
limiter is too cautious and capacity is higher than reported; if it does and also counts rejected retries, naive
retrying is even worse. **Not built:** the web server with streaming to users (load runs drive the pipeline
in-process), and request coalescing. **Limitations:** 40 retrieval / 17 answer questions; 4–7 corruption items per type
(the judge caught 7/7 wrong sources but 4/7 appended claims); the numeric-grounding check was designed after seeing those
misses (post-hoc, same items); a chunk is labelled with the section it starts in, so a citation's section can be wrong
while its page is right; no stemming ("parameters" vs "7B-parameter"); stand-in assumptions as listed.
